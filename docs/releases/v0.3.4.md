# Ignition v0.3.4

Ignition runs YOLO26, the newest YOLO family, at 3.41x AMD's Ryzen AI stack and 8.91 mAP@50-95 more accurately on the same quantized weights. It is the widest gap on any model Ignition runs, because YOLO26's two attention blocks stop AMD's Vitis AI EP almost completely: it places 12 of the model's 1,526 graph nodes on the NPU, where the engine runs 107 of 107 layers. The installer also survives a fresh machine better, and two `--task` values that used to crash now refuse with a message. The ignite-xdna wheel attached here is 0.3.2; the `npu` extra now requires it.

## What changed

- **YOLO26n on the NPU, with no SDK change.** YOLO26 dropped DFL, so its box head carries four channels instead of 4x16. The container declares that as `reg_max` and ignite-xdna's decode follows it, so nothing in Ignition knows a model by name (ignite-xdna `266802f`, `4cc03df`, `c16daca`). Ignition takes its boxes from the NPU detect heads on 500/500 timed frames, and the container's two attention cores make exactly 2 `onnxruntime.InferenceSession.run` calls per frame, counted in a harness, against 0 for YOLOv8n and 1 for YOLO11n.
- **It needs ignite-xdna 0.3.2.** `reg_max` became a container property after 0.3.1 was cut, so the released 0.3.1 wheel cannot decode a YOLO26 head and the old `>=0.3.1` pin could not tell the two apart. The `npu` extra now requires `ignite-xdna>=0.3.2`.
- **A guard against a stale manifest.** A container compiled before `reg_max` was derived can declare 16 beside a four-channel box head. Decoding one reduces over DFL bins that are not there: it does not raise, it returns wrong boxes. ignite-xdna now refuses that combination, naming both numbers (`c16daca`).
- **The installer refreshes PATH after winget, and says which step failed.** A fresh machine stopped at step 7 of 10, which runs eight commands and reported only a label and an exit code. Each now throws with its own name and the full command line. `Update-ProcessPath` rebuilds `$env:Path` from the registry after each winget install, because winget writes PATH there while the running process keeps the environment it started with (`c7efbb3`). The original failure is **not reproduced** on the development machine, where two full scratch-root runs reached `[10/10] Checks` and exited 0, so this is a fix for one class of fresh-machine failure plus the diagnostics the next report needs.
- **`--task segment` and `--task matte` refuse instead of crashing.** Both are advertised by the CLI, and on an `.ignite` container both raised a bare `ModuleNotFoundError` for `ignite_xdna.runtime.dense_session`, which no released ignite-xdna provides. They now raise a message naming what is missing. Their hybrid engine path and their measurements are still pending.

## Measured

Ryzen 7 8700G (8 cores, 16 threads), NPU Device 0, Windows 11, Ignition in its default `balanced` power mode, 50 warm-up and 500 timed frames of `bus.jpg` per run, stacks interleaved, two runs each, 2026-09-21. `xrt-smi` showed no hardware contexts before every run and after the last.

| Run | Result | Record |
|---|---|---|
| YOLO26n, Ignition with `--silu-sigmoid` | **11.03 / 11.01 ms** | ignite-xdna `results/aie/yolo26n_ignition_sitting_20260921.log` |
| YOLO26n, AMD Ryzen AI 1.7.1 | 37.44 / 37.67 ms | the same sitting, arms alternating |
| YOLO26n, Ignition without the flag | 10.73 / 10.71 ms | the same sitting, so the flag costs 0.30 ms |
| YOLO26n COCO mAP@50-95, all 5,000 val2017 | **32.55** against AMD's **23.64** | ignite-xdna `results/aie/yolo26n_silu_recovery_20260921.log` |

AMD's arm decoded through `npu.yolo26_decode`, added to ignite-xdna's `tools/amd_vitisai_yolo.py` as `--decoder`: the YOLOv8-shaped decode cannot read a four-channel box head and would have placed every box wrongly without raising.

**The accuracy caveat travels with the number.** YOLO26n's own float export scores **39.66** on the same harness, so 32.55 is 7.11 below float. The win is against AMD's stack on identical quantized weights, not against the float model. Without the epilogue the container scores 23.74, within 0.10 of AMD's 23.64, which is what two stacks running a layer-exact container should read.

**Not measured here.** Energy, for either stack on this model. Both AMD runs reported `EP report node devices report not found`, so the 12-of-1,526-nodes placement is an earlier session's and is not re-confirmed by this one. The installer fix is unconfirmed on a genuinely fresh machine.
