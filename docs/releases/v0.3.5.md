# Ignition v0.3.5

Every model Ignition runs was measured against AMD's Ryzen AI stack again, in one pre-registered sitting, and the
answer is mixed and now stated per model. Ignition is faster end to end on YOLOv8n, YOLOv8n-pose, YOLO11n (3.7x) and
YOLO26n (3.4x). AMD's stack is faster on SESR M7, on YOLOv8m, l and x, and on YOLOv8s once its compiler is tuned.
The README now says so in one table. The installer also gets through networks that stopped it before.

## What changed

- **A new README.** A banner, the badges, and a table of every model: what runs on the NPU, and which stack is faster.
  Figures stay in `docs/PERFORMANCE.md`, which opens with the new sitting.
- **The walkthrough builds its own model.** Steps 2-4 now follow the quickstart steps of ignite-xdna's
  [yolov8n recipe](https://github.com/jdominick05/ignite-xdna/blob/main/recipes/yolov8n.toml). They download
  Ultralytics' v8.3.0 weights (the file the recipe pins), calibrate on coco128, and write
  `models/yolov8n_cut_xint8_coco128.onnx` and `build/yolov8n_quickstart.ignite`. Before, they wrote over
  `yolov8n_cut_xint8.onnx`, the file the benchmark container is compiled from. The README says the badges measure the
  recipe's benchmark model, calibrated on other images.
- **Installer fixes for fresh machines and filtered networks.**
  - A bare winget call made `Get-Python` return an array, and step 7 tried to run it as a command. That was the
    fresh-machine failure behind v0.3.4's PATH change (`5f5b826`).
  - The package installs retry (`d0b7279`).
  - mlir-aie and llvm-aie are fetched by direct wheel URL rather than through a `--find-links` HTML page, which a
    filtering network blocked while letting the wheels themselves through (`a3c2171`).
  - `docs/USAGE.md` says what to do when the installer stops on a filtered or throttled network.
- **Source headers name the Ignition contributors.** They had named AMD as copyright holder of code written here
  (`6a9f093`). The licence is unchanged: AGPL-3.0-or-later.
- **`--task segment` and `--task matte` give a clearer refusal.** The message now says the dense engine path is in the
  ignite-xdna source checkout but in no released wheel, and that both tasks run slower than AMD's stack.
- **`ignition.experimental`** holds a hybrid Gemma assistant, a workspace agent and a prefix-bound assistant
  (`85d35d9`). They need the ignite-xdna research checkout and are **not supported in this release**: no speed, energy
  or unattended-operation claim is made for them.

## Measured

Ryzen 7 8700G, Phoenix NPU, Windows 11, 2026-10-19. Ignition at `85d35d9` (the sitting's logs call it `c16abb2`, the
same tree before its trailer was rewritten) in the default `balanced` power mode, on containers built by
ignite-xdna's recipes, each matched to its reference on every layer on the NPU first. 50 warm-up and 500 timed frames
of `bus.jpg` per run, two interleaved rounds, the NPU idle before every run. Glass to glass, mean ms, rounds 1 / 2:

| Model | Ignition | AMD Ryzen AI 1.7.1 | Faster |
|---|---|---|---|
| YOLOv8n | **7.16 / 7.15** | 10.83 / 10.84 (tuned 10.17 / 10.26) | Ignition |
| YOLOv8s | 15.77 / 15.77 | 17.22 / 17.25 (tuned **14.60 / 14.66**) | Ignition against the default; AMD tuned |
| YOLOv8n-pose | **7.50 / 7.50** | at least 9.18 / 9.15 | Ignition |
| YOLO11n | **9.85 / 9.88** | 36.98 / 36.22 | Ignition |
| YOLO26n | **10.83 / 10.77** | 37.19 / 37.18 | Ignition |
| SESR M7 | 4.46 / 4.54 | **3.97 / 4.26** | AMD |
| YOLOv8m | 39.18 / 39.23 | **31.95 / 31.95** | AMD |
| YOLOv8l | 69.96 / 69.97 | **51.47 / 51.47** | AMD |
| YOLOv8x | 112.90 / 113.00 | **78.93 / 79.00** | AMD |

Record: ignite-xdna `results/aie/release_resit_20261019/` (pre-registration, logs, per-stage table), in BENCHMARKS
under "The release re-sit against AMD's stack".

- **Where each lead comes from.** On YOLOv8n and YOLOv8s the network itself is level or faster on AMD's side; Ignition's
  lead is its native image preparation and box decoding, against the numpy reference code AMD's arm used. On YOLO11n
  and YOLO26n the lead is in the network: AMD's EP cannot place their attention blocks.
- **AMD's pose tool prints no frame mean**, so its pose figure is its `session.run` time alone, a lower bound.
- **Accuracy was not re-measured.** The containers are exact against their references, so the COCO figures on the
  badges stand: 34.12, 34.63, 32.55 and 44.16 OKS mAP@50-95 against AMD's 26.68, 25.82, 23.64 and 32.64.
- **The walkthrough as written** ran on a scratch `install.ps1 -InstallRoot` in Windows PowerShell 5.1: calibration
  316.5 s, compile 14.7 s, `bus.jpg` at 7.181 ms mean over 100 headless frames with 5 detections from the NPU heads
  (recorded in `074b141`).

**Not measured here:** energy, memory and install size (those badges read earlier sittings); the performance power
mode; the walkthrough in PowerShell 7; the installer fixes on a genuinely fresh machine behind a filtering network.
